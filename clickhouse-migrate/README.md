# clickhouse-migrate

Applies the [golang-migrate](https://github.com/golang-migrate/migrate) SQL
migrations in [`config/clickhouse-migrations/migrations`](../config/clickhouse-migrations/migrations)
to a ClickHouse database, authenticating with a **client TLS certificate**
instead of a password (see `users.d/ssl_auth.xml` on the ClickHouse side).

It runs as a Kubernetes Job (`config/clickhouse-migrations/job.yaml`); the
migration files are mounted from a ConfigMap generated by kustomize, so adding
a `.sql` file means also adding it to `kustomization.yaml`.

On startup it creates the target database if it doesn't exist, then applies
every pending migration. Re-running is a no-op.

## Configuration

| Env var | Required | Default |
| --- | --- | --- |
| `CLICKHOUSE_HOST` | yes | |
| `CLICKHOUSE_USER` | yes | |
| `CLICKHOUSE_DATABASE` | yes | |
| `CLICKHOUSE_PORT` | | `9440` |
| `MIGRATIONS_DIR` | | `/migrations` |
| `MIGRATIONS_TABLE` | | `schema_migrations` |
| `CLICKHOUSE_TLS_CERT_FILE` | | `/etc/clickhouse-client/certs/tls.crt` |
| `CLICKHOUSE_TLS_KEY_FILE` | | `/etc/clickhouse-client/certs/tls.key` |
| `CLICKHOUSE_TLS_CA_FILE` | | `/etc/clickhouse-client/certs/ca.crt` |

The Job targets the first replica directly rather than the load-balanced
Service: with a Replicated engine, DDL from any one replica reaches them all,
and it keeps concurrent migrations from racing.

## Writing a migration

1. Name files `NNNNNN_description.up.sql` / `.down.sql`.
2. **Don't qualify object names with a database** (`logs`, not `o11y.logs`) —
   the connection is already scoped to `CLICKHOUSE_DATABASE`, and a hardcoded
   prefix silently writes to the wrong place.
3. **Prefer one statement per file.** ClickHouse rejects multiple statements in
   a single query, so the driver runs with `MultiStatementEnabled` and splits
   files on `;` *textually*. That means a semicolon inside a string literal,
   quoted identifier, or comment gets cut in half and sent as two broken
   queries. One statement per file keeps you out of that territory entirely.
4. Add both files to `config/clickhouse-migrations/kustomization.yaml`.

`TestMigrationFiles_SafeToSplit` enforces rule 3 and `TestMigrationFiles_Unqualified`
rule 2, so a bad file fails CI rather than a deploy:

```sh
task clickhouse-migrate:check-migrations
```

## Creating a client shell

For when you need to connect to the database via a shell (for instance, to
recover from a dirty database).

```
kubectl apply -f ch-shell.yaml

kubectl -n o11y-system exec -it ch-shell -- clickhouse-client \
  --host chi-clickhouse-o11y-0-0.o11y-system.svc.cluster.local \
  --port 9440 --secure --user clickhouse-migrations-client

# container has live creds, so delete the container when you're done

kubectl -n o11y-system delete -f ch-shell.yaml
```

## Recovering from a dirty database

migrate marks a version dirty *before* running it, so a migration that fails
partway leaves the database at `Dirty database version N` and every subsequent
run refuses to proceed until someone intervenes:

```
applying migrations: Dirty database version 1. Fix and force version.
```

That message is the *symptom*, not the cause — the real error is in the logs of
the **first** attempt (the Job retries, and every retry after the first fails
this way). Find it, fix the migration, then reconcile the recorded version with
what actually landed in the database: either finish/undo the partial statements
by hand and `UPDATE`/re-insert the version row, or, if nothing applied, drop the
bookkeeping table and re-run the Job:

```sql
DROP TABLE IF EXISTS <database>.schema_migrations
```

## Development

```sh
task clickhouse-migrate:build              # build the binary
task clickhouse-migrate:test               # unit tests + migration file checks
task clickhouse-migrate:test-integration   # + apply migrations to a throwaway ClickHouse (needs docker)
task clickhouse-migrate:lint
```

`test-integration` starts a container, applies the real migration set to an
empty database, and checks the result; the tests that need it skip when
`CLICKHOUSE_TEST_ADDR` is unset, which is why plain `task test` stays offline.
